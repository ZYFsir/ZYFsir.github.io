写上一篇 Agent 架构演变史的时候，有一个时刻让我愣住。

写到 SOAR（1987）的 Chunking 机制时，我意识到它和今天 Hermes Agent 的 SKILL 系统几乎做的是同一件事：**把成功的经验编译成可复用的规则，下次直接调用。** 我当时的原话是——

> 要我说，ReAct 循环完全跟这个一样，所以算不上什么新东西。

这不是故作惊人之语。顺着这个思路往下挖，我发现 SOAR 的整个记忆架构在今天看都不过时。不仅不过时，它还比大部分号称有"记忆系统"的产品更完整。

但这引出一个让我不太舒服的问题：

**一个 1987 年的架构就已经想清楚的事，为什么 2026 年还在被当作创新来营销？**

或者说更尖锐一点：记忆系统，真的是 Agent 性能的关键瓶颈吗？

但要把这个问题讲透，光知道"SOAR 有 9 层记忆"是不够的。我一开始就是跳到结论，跳过了太多细节。所以这篇文章先停下来，**把 SOAR 到底是什么彻底弄清楚**，再回头看今天的 Agent 架构，才能真正看出门道。

## 一、SOAR 是什么——一个会思考的系统

SOAR（State, Operator And Result）由 Allen Newell、John Laird 等人在 1987 年提出。它的目标是实现通用人工智能——用的还是符号主义那套方法。

SOAR 不是"一个 AI 程序"。它是一套关于智能的理论：任何表现出通用智能的系统，都得有某种固定的结构——包含什么记忆系统、什么决策流程、什么学习机制。

### 1.1 九层记忆

在这个框架里，记忆不是附加功能，是核心架构。SOAR 一共定义了 **9 个记忆系统**，分三层：

**工作记忆**——SOAR 的全局工作空间。所有感知输入、中间推理状态、决策状态都在这里，用栈结构分层表示目标与子目标。相当于今天 Agent 的 Scratchpad + 对话历史。

**长期记忆**分三个独立系统：

| 记忆类型 | 内容 | 今天的对应物 |
|:---------|:-----|:------------|
| **程序性记忆**（Production Rules） | if-then 规则，决定怎么做 | LLM 的权重 + 推理策略 |
| **语义记忆**（Semantic Memory） | 事实性知识，知道是什么 | RAG 知识库 / 向量数据库 |
| **情节记忆**（Episodic Memory） | 过去的经验，经历过什么 | 对话历史 / 记忆流 |

**意向记忆**——SOAR 还有一个 Goal Stack（目标栈），管理当前正在追求的子目标及其优先级。这对应今天 Agent 的任务队列和规划器。

但光知道这些表格太浅了。下面来看 SOAR 到底**怎么运作**的。

### 1.2 决策周期

SOAR 的核心是一个固定循环，称为**决策周期**。每个周期分四个阶段：

```
输入 → 细化（规则匹配） → 决策 → 输出
                ↑              |
                └── 学习 ──────┘
```

**细化阶段**（Elaboration Phase）：所有规则（Productions）同时与当前工作内存匹配。使用 **Rete 算法**——一个增量匹配网络。工作内存变化时，只有变化的部分被传播，不需要每条规则重新扫描全部条件。这是 SOAR 能实时运行的关键工程保障。

这个阶段里会发生几类事情：
- 状态细化（从已有信息推导出新事实）
- **Operator 提案**（创建候选操作符 + 偏好）
- Operator 选择偏好（告诉决策程序哪个更好）
- **Operator 应用**（如果已有选中操作符，执行它改变状态）

**决策阶段**（Decision Phase）：决策程序消费所有偏好，为一个状态选出一个操作符。如果偏好不足以唯一确定，就进入困境。

**输出阶段**：选中操作符产生的输出命令通过 output-link 发送到外部环境。

### 1.3 偏好系统——规则如何"吵架"

SOAR 没有写死的 `if-else if-else` 链。**所有规则同时触发，通过偏好系统竞争。**

规则可以声明 11 种偏好：

| 偏好 | 符号 | 含义 |
|:----|:----|:-----|
| 可接受 | `+` | 这是一个候选操作符 |
| 更好 | `>` | O1 比 O2 更好 |
| 最好 | `!` | 所有操作符中最好的 |
| 更差 | `<` | O1 不如 O2 |
| 最差 | `!!` | 所有操作符中最差的 |
| 拒绝 | `-` | 禁止选择该操作符 |
| 无所谓 | `=` | 从候选池中随机选 |
| 数值无所谓 | `= <num>` | 带权重的无所谓（RL 使用） |
| 需要 | `!+` | 必须选这个 |
| 阻止 | `!-` | 禁止创建这个 WME |

决策程序按顺序处理：先应用拒绝/需要约束，再缩小候选集到最好，再用更好/更差比较。如果最后还剩多个，就看无所谓——等于"随便挑一个"。

这种设计意味着：**SOAR 的"智能"不是来自某一条聪明的规则，而是来自规则之间的竞争关系。** 一个操作符被选中，不是因为某条规则定义了它，而是因为支持它的偏好权重总量压过了其他偏好。

### 1.4 i-support 与 o-support

规则创建的工作内存元素有两种生命期：

- **i-support**（意图支持）：只要创建它的规则条件还满足，WME 就存在。条件不再满足时自动撤回。用于状态细化和操作符提案。
- **o-support**（操作符支持）：由操作符应用规则创建，一旦创建就持久存在，即使创建规则不再匹配。用于执行操作符后的状态改变。

这个区分是 SOAR 核心设计之一：你既需要自动清理的临时数据（比如提案），又需要持久化的状态变化（比如"我已经移动过了"）。大部分 Agent 框架没有明确区分这两种需求。

### 1.5 一条真实的 sp 规则

SOAR 的规则用 `sp`（Soar Production）声明。下面是一条提案规则，逻辑是"如果角色前方没被挡住，就提议向前走"：

```
sp {propose*move-forward
   (state <s> ^io.input-link.blocked.forward no)
   -->
   (<s> ^operator <o> +)
   (<o> ^name move-forward)}
```

`+` 是"可接受"偏好，告诉决策程序这是一个候选操作符。下面的规则是对应的应用规则，真正执行动作：

```
sp {apply*move-forward
   (state <s> ^operator.name move-forward
          ^io.output-link <out>)
   -->
   (<out> ^move <m>)
   (<m> ^direction forward)}
```

输出命令挂到 output-link 上，外部环境（游戏引擎、模拟器）读取后执行。

## 二、困境驱动的问题求解

SOAR 区别于所有普通状态机的核心设计是：**困境驱动的问题求解。**

### 2.1 四种困境

当决策程序无法确定选哪个操作符时，架构自动进入困境：

| 困境类型 | 触发条件 |
|:---------|:---------|
| **平局**（Tie） | 多个操作符都可选，但偏好不足以区分 |
| **冲突**（Conflict） | 偏好互相矛盾（O1 > O2 且 O2 > O1） |
| **约束失效**（Constraint Failure） | 所有候选都被拒绝，或必须选但没有候选 |
| **无变化**（No Change） | 选中操作符但应用后状态没变 |

### 2.2 困境 → 子目标

当困境发生时，SOAR **自动创建一个子状态（子目标）**。这个新状态自动获得：
- `^superstate <父状态>`（指向父状态）
- `^impasse <困境类型>`（记录为什么被卡住）
- 自己的一套 I/O 链接、操作符提案、偏好系统

子目标的任务就是解决父状态遇到的困境。例如：
- **平局困境**：子目标可以在内部模拟搜索，比较各个候选操作符的后果，然后返回一个偏好给父状态
- **无变化困境**：子目标可以把一个操作符分解成更细的步骤

### 2.3 与 ReAct 的对应

你上一篇提到的"ReAct 循环完全跟这个一样"——这里就是确切的证据。

现代的 LLM Agent 循环（Think → Act → Observe → Repeat）中，当 LLM 说"让我想想"或"我需要先查一下"时，它其实是在创建一个隐式的子目标。区别在于：

- **SOAR**：子目标是架构自动创建的，有固定的生命周期，解决后自动收回，通过 Chunking 记忆经验
- **ReAct**：子目标是 LLM 在 prompt 里自己生成的，没有架构级别的管理，不自动学习

SOAR 把"思考"和"行动"放在了同一个结构框架里。ReAct 用 prompt 模拟了这个框架，但没有底层的结构保障。

### 2.4 子目标解决后：Chunking

当子目标找到解法（向父状态返回了结果），Chunking 机制自动触发：**把在整个子目标中推导出结果的过程编译成一条新的生产规则。**

这意味着：之前需要 10-50 步推理才能解决的问题，下次遇到时一条规则就解决了。

## 三、一个完整的 Blocks-World Agent

理论够多了。看一个实际运行的系统。

### 3.1 问题定义

积木世界（Blocks World）：三个积木 A、B、C 在桌子上，目标是把它们堆叠成 A 在 B 上、B 在 C 上、C 在桌子上。

### 3.2 规则伪代码

一个最简 SOAR 求解器只需要这几条规则：

```
规则1（状态细化）：桌子永远是空的（上面可以放东西）
    如果 <桌子> 是桌子 → 标记 <桌子> 为空

规则2（状态细化）：一个积木没有被其他积木压着 → 它是空的
    如果 <积木> 是积木，且没有 <其他积木> 在它上面 → 标记 <积木> 为空

规则3（提案）：把一个空的积木移动到另一个空的位置
    如果 <A> 是空的，<B> 是空的，且 A 不在 B 上
    → 提案操作符 move(A到B)

规则4（选择偏好）：所有 move 操作符随机选
    任何 move 操作符 → 标记为"无所谓"

规则5（应用）：执行移动
    如果选中 move(A到B)
    → 删除旧的 A 的位置信息，添加 A 在 B 上

规则6（检测目标）：A在B上，B在C上，C在桌子上 → 完成
```

### 3.3 逐周期推演

**初始状态**：A、B、C 都在桌子上，都是"空的"。

**决策周期 1**：
1. 细化：A、B、C 都标记为空，桌子标记为空
2. 提案：规则 3 匹配了所有"空积木→空位置"的组合——A→B, A→C, A→桌子, B→A, B→C, B→桌子, C→A, C→B, C→桌子（9 个候选）
3. 偏好：规则 4 给所有候选标记为"无所谓"
4. 决策：架构随机选了一个，比如 B→C
5. 应用：规则 5 执行，B 放到 C 上面

**决策周期 2**：
1. 细化：现在 B 在 C 上，所以 C 不再是空的。A 和桌子仍是空的
2. 提案：候选操作符变少（A→B, A→C, A→桌子, C→A, C→桌子, B→A, B→桌子... 但很多不再满足"空"条件）
3. 决策：再次随机选一个
4. ...

**最终决策**：当 A 在 B 上、B 在 C 上、C 在桌子上时，规则 6 匹配 → 打印"完成" → halt

### 3.4 关键洞察

这个过程中没有任何"智能"——没有启发式搜索，没有规划，只有规则竞争和随机选择。**SOAR 的智能从来不是某条规则聪明，而是规则之间的交互在决策周期的约束下产生了有方向的搜索行为。**

如果加上 Chunking：当子目标通过搜索找到一条路径后，Chunking 会把整条路径编译成一条规则。下次从同一初始状态出发，**一步决策就完成**，不需要再搜索。

## 四、SOAR 的四项学习机制

SOAR 有四种不同的学习方式，各自对应不同的记忆系统：

### 4.1 Chunking（程序性学习）

- **存储形式**：新的 `sp` 规则
- **触发条件**：子目标产生结果时自动触发
- **算法**：基于解释的行为摘要（EBBS），使用身份图进行泛化
- **效果**：把子目标中的多步推理编译成单条规则。手册称"数百次规则触发可以被压缩为一次"
- **正确性**：通过身份泛化保证在给定抽象级别上的正确性

### 4.2 强化学习（数值学习）

- **存储形式**：操作符上的数值权重（数值 indifferent 偏好）
- **算法**：Sarsa 或 Q-Learning
- **奖励**：通过每个状态上的 reward-link 结构提供
- **探索**：epsilon-greedy 或 Boltzmann softmax
- **与 Chunking 的关系**：RL 规则本身也是规则，所以可以被 Chunking 进一步编译——实现了复杂关系结构中的 RL

### 4.3 语义记忆（事实性知识）

- **存储形式**：LTI（长时标识符），存储在 SQLite 中
- **检索**：线索匹配或直接 LTI 名称访问
- **激活**：基于最近性、频率、上下文扩散激活
- **性能**：手册称"亚毫秒级检索"，支持数百万节点

### 4.4 情节记忆（经验性知识）

- **存储形式**：工作内存的完整时间快照
- **编码**：自动存储（可配置频率）
- **检索**：基于线索的最近邻匹配
- **用途**：通过回忆过去类似情况进行类比推理

### 4.5 总结对比

| 维度 | Chunking | RL | 语义 | 情节 |
|:-----|:---------|:---|:-----|:-----|
| 存储形式 | 产生式规则 | 数值权重 | LTI 图 | 时间快照 |
| 获取方式 | 经验编译 | 试错 | 显式存储 | 自动记录 |
| 泛化性 | 高（通过身份图） | 高（函数逼近） | 中（精确匹配） | 低（线索匹配） |
| 先决条件 | 困境+子目标 | 奖励信号 | 存储命令 | 激活的记忆 |

## 五、SOAR 的成就与今天

### 5.1 TacAir-Soar（1990 年代）

SOAR 有史以来最大的部署，由密歇根大学和美国空军合作开发：
- **5200 条规则**（手工编写 + Chunking 学习）
- 同时跑 **30-60 个自主 Agent** 驾驶 F-15 模拟飞行
- 行为覆盖：空战、编队飞行、任务规划、通信、威胁规避
- 通过 ModSAF 模拟器连接，接收雷达数据、输出飞行控制指令
- 在 200MHz 机器上每 50ms 完成一次决策

这是 1990 年代最复杂的 AI 系统之一。它证明了符号架构可以扩展到现实世界的实时领域。

### 5.2 其他里程碑

- **SOAR QuakeBot**：实时玩 Quake II 的 SOAR Agent
- **Infinite Mario RL**：用强化学习玩 Super Mario
- **Interactive Task Learning**：从自然语言交互中学习新任务

### 5.3 SOAR 今天还活着

**最新版本 9.6.5**（2025 年 7 月）。功能特性：
- `$` 字面化操作符——更精细控制 Chunking
- CMake 构建系统迁移中
- SWIG 绑定：Python、Java、Tcl、C#、JavaScript
- VisualSoar 可视化开发环境
- 语义记忆支持 LTI 别名
- 周期性发布，GitHub 10000+ 次提交

**开源生态**：

| 项目 | 说明 |
|:-----|:-----|
| SoarGroup/Soar | C++ 内核，420 stars，BSD 许可 |
| JSoar | SoarTech 维护的纯 Java 实现 |
| Engineer's Guide to Soar | 14 讲程序员教程 |
| soar-sml | Python 包：`pip install soar-sml` |
| soar_ros | ROS2 机器人集成 |
| VisualSoar | Java 可视化开发环境 |

**2024-2025 年新方向**：
- **NL2GenSym**：用 LLM 从自然语言生成 SOAR 符号规则（密歇根大学，2025）
- **LLM-Modulo 认知系统**：LLM 作为 SOAR Agent 的"顾问"，处理开放域问题
- **SOAR + ROS**：控制真实机器人
- **多无人机协同决策**（Drones, 2025）
- **SOAR + 深度强化学习**混合策略（Neurocomputing, 2025）

### 5.4 你可以试什么

想亲手体验 SOAR，按难度从低到高：
1. 下载 `SoarSuite_9.6.4-Multiplatform.zip`（41MB），跑 Eaters Demo（类 Pac-Man）
2. 跟官方 8 部分教程写自己的规则
3. `pip install soar-sml` 用 Python 控制 SOAR 内核
4. 跑 Blocks-World / Water Jug / TankSoar 等内置例子

## 六、符号 AI 没有死——游戏中的实际应用

现在放下 SOAR 本身，看一个更大的画面。

SOAR 代表的符号 AI 路线——状态、操作符、规则、偏好——在今天不仅没有消失，反而以各种形式统治着游戏产业。**每年数百亿美元的游戏行业，95% 以上的 AI 决策系统是符号的。**

### 6.1 F.E.A.R. 的 GOAP（2005）

Monolith 的 Jeff Orkin 设计了 Goal-Oriented Action Planning。每个 AI 士兵有一套动作，每个动作定义前提条件和效果：

```
动作: "射击"
  前提: 敌人可见, 有武器, 有弹药
  效果: 敌人受伤
  消耗: 3.0

动作: "换弹夹"
  前提: 有武器, 没弹药, 附近有弹药源
  效果: 有弹药
  消耗: 2.0

动作: "找掩护"
  前提: 附近没有掩护
  效果: 在掩护中
  消耗: 5.0

动作: "侧翼包抄"
  前提: 敌人可见, 队友在交战
  效果: 敌人在侧翼暴露
  消耗: 6.0
```

当 AI 要执行"杀死敌人"的目标时，GOAP 规划器用 A* 从目标状态向后搜索，找出一串动作序列。结果是涌现式的——设计师自己都未必预料到 AI 会以什么顺序组合动作。Glenn Fiedler 在 AI Postmortem 中提到："测试时我们经常看到 AI 做出我们没教过它的战术组合。"

Monolith 从 F.E.A.R. 到 Shadow of Mordor 的宿敌系统，一直使用 GOAP。

### 6.2 Halo 2 的行为树（2004）

Bungie 的 Damien Boulton 设计了最早的游戏行为树。每个 Covenant 精英的 AI 组织成树形结构：

```
精英行为树
├── 侦查（听到可疑声音）
├── 搜索（最后已知玩家位置）
├── 交战
│   ├── 压制射击（一人射击，其他人包抄）
│   ├── 包抄
│   ├── 冲锋（狂战士模式，仅限 Grunt）
│   └── 撤退（伤亡过多）
└── 巡逻（默认）
```

行为树从 Halo 2 开始成为行业标准。Unreal Engine 内置了完整的 BT 系统，几百款商业游戏在用。**有限状态机（FSM）+ 行为树 + Utility AI 构成了今天游戏 AI 的绝对主力。**

### 6.3 RDR2 的海量状态机（2018）

Rockstar 用最朴素的符号系统做到了令人惊叹的规模：

**NPC 日程系统**：每个有名 NPC 有 7-10 个时间槽的固定日程：

```
(6:00 起床 → 6:30 吃早餐 → 7:30 去镇上开工
 → 12:00 午餐 → 13:00 继续工作 → 18:00 去酒馆
 → 21:00 回家 → 22:00 睡觉)
```

每个时间槽是一个状态，带路径点 + 动画混合 + 天气变量（下雨时躲雨）。

**荣誉系统**：-8 到 +8 的纯规则系统。
- 杀无辜 NPC：-2.0
- 帮助陌生人：+0.25 ~ +1.0
- 打招呼：+0.01
- 钓鱼放生：+0.05
- 荣誉等级影响商店折扣、对话内容、结局

**目击/犯罪系统**：玩家犯罪 → 目击者震惊（2-3 秒）→ 跑去报警 → 如果中途被杀则不了了之 → 警长进入调查 → 看到玩家则根据罪行决定逮捕/击毙 → 如果拒捕则通缉等级升级。

**全部是手写规则，没有任何机器学习。**

### 6.4 行业数据

根据 GDC 调查等行业估计：

| 技术 | 使用率 |
|:-----|:------|
| 有限状态机 | 80-90% |
| 行为树 | 50-70% |
| Utility AI | 10-20% |
| GOAP / 规划器 | 5-10% |
| ML / 强化学习（已发售游戏） | < 5% |
| 神经网络决策（已发售游戏） | < 1% |

ML 在游戏中的实际应用集中在动画控制（RL 动作生成）和对话（LLM），不是核心战术决策。**游戏 AI 的决策层至今是符号系统的地盘。**

### 6.5 这说明什么

符号 AI 没有消失。它退出了"用手写规则覆盖一切知识"的狂妄尝试——那确实是 SOAR 和专家系统在 1980 年代失败的原因。但在**受限领域内做确定性的可靠决策**这件事上，符号系统至今无可替代：

- 你能对一个神经网络说"这个分支永远不会被执行"吗？
- 你能对神经网络做形式化验证吗？
- 你能在神经网络上保证 50ms 最坏情况延迟吗？

符号系统能。

F.E.A.R. 的 GOAP 本质上就是 STRIPS（1971）的直接后裔。Halo 的行为树和 SOAR 的偏好系统共享同一个设计思路：**用结构化的方式组织决策逻辑。** 30 年过去了，游戏行业用行为树做 SOAR 想做的事情，只不过环境是虚幻引擎而不是 ModSAF。

## 七、检索式记忆的理论天花板

抛开营销回到技术层面：今天的"记忆系统"本质上都是检索式记忆——你存一段文本，下次用向量搜索找到它，再塞回上下文。

这个范式有一个**数学层面无法规避**的问题。

### 7.1 高维诅咒

你能想到的几乎所有嵌入模型都在用 768d 或 1024d 的向量。

Aggarwal 等人在 2001 年就证明了一个令人不安的事实：当维度超过约 25 时，高维空间中所有点的距离趋向均匀。最近邻和最远邻的距离比值趋近于 1。

这意味着：**你的向量索引本质上是一个随机排序器，** 只是被嵌入模型的"语义压缩"勉强维持着秩序。两个文档余弦相似度 0.85 可能语义无关，另外两个 0.80 可能是同义改写。你的 ANN 索引分辨不了这个区别。

你提高召回率=扩大检索范围，必然引入噪声——因为决策边界一定包含边界线不相关的文档。

### 7.2 Lost in the Middle

Liu 等人（2023）发现 LLM 在长上下文上的表现呈 U 型曲线：相关信息在开头和结尾时性能最好，在中间时下降 20-40%。

这意味着：**你为了提高召回率多检索几个文档进去，这些文档恰好被塞进了模型最不会利用的位置。**

你在主动伤害自己。

更糟糕的是，这个 U 型是因果注意力（Causal Attention）的结构性属性。长上下文模型（128K、200K、甚至 1M）都没有消除它。它是一个 architectural 问题，不是一个参数能调好的。

### 7.3 LLM 对噪声的极度敏感

Shi 等人（2023）在 GSM-IC 基准上发现：**一个无关句子就让 GPT-3 的准确率从 80% 掉到 55-65%。** 一个句子。

Cuconasu 等人（2024）进一步揭示：主题相关但实际无关的文档**比明显无关的文档更有害**——因为 LLM 分不清"看起来相关但没用"和"真正有用"。

把这三个事实串起来：

| 事实 | 含义 |
|:----|:-----|
| 高维诅咒 | 提高召回率不可避免引入噪声 |
| Lost in the Middle | 多塞的文档在模型最不擅长的位置 |
| 噪声敏感 | 少量噪声就显著降低输出质量 |

这就是 Precision-Recall 矛盾的完整图景。它不是工程问题，是**结构性问题**。

### 7.4 实证：记忆增益的边际递减

我不是在说记忆系统没用。它确实有效。Hindsight（2025）把 20B 模型在 LongMemEval 上从 39% 提升到 83.6%。CorpGen（2026）把多任务完成率从 8.7% 提升到 15.2%（3.5x）。

但同一批论文也揭示了一个天花板：

- Zep 在 MemGPT 自己的基准上只领先 **1.4 个百分点**
- Lian 等人（2024）发现记忆超过 500 个事件的 Agent 产生矛盾计划的概率是小于 50 个事件的 **2 倍**
- 学术界开始承认：当前 RAG 范式的记忆系统正在逼近收益天花板

## 八、SOAR Chunking vs 现代 Agent 的"学习"

回到 SOAR。它的 Chunking 和今天的"记忆"有一个**本质性的区别**：

| 维度 | SOAR Chunking | 现代 Agent 记忆 |
|:-----|:-------------|:---------------|
| 改变了什么 | 新增生产式规则到架构中 | 存一段文本到数据库 |
| 持久性 | 永久的行为改变 | 依赖上下文窗口（滚出去就没了） |
| 机制 | 条件-动作规则编译 | 文本注入到 prompt |
| 泛化 | 规则自动匹配任何符合条件的状态 | 只有文本重新注入才生效 |
| 重量级 | 轻量（一条规则） | 重量级（每次检索 + 上下文消耗） |

**SOAR 的 Chunking 是真正的程序性学习**：系统的决策逻辑被永久修改了。下次遇到同样的情况，它不需要思考，直接反应。

**现代 Agent 的"记忆"是外部文本存储**：每次使用都需要重新检索、重新注入、让模型重新处理。你记了 100 件事，每次对话开始，你要检索一次，消耗一次上下文。

这不是同一个量级的东西。

Hermes Agent 的 SKILL 系统是最接近 Chunking 的——它在完成任务后自动创建 SKILL 文件——但它依然只是存了一段文本，下次读取这段文本。模型权重从未被修改过。

所有号称"终身学习"的产品都得打上问号。

## 九、Harness 工程：被忽视的真正杠杆

如果记忆不是 Agent 性能的关键瓶颈，那什么是？

越来越多的证据指向另一个方向：**Agent 与环境的接口质量——工具设计、反馈信号、错误处理、状态控制。** 我称之为 Harness 工程。

### Andrew Ng 的数据

2024 年 3 月，Andrew Ng 在 Agentic Design Patterns 系列中公布了一个令人震惊的对比：

| 配置 | HumanEval 准确率 |
|:-----|:----------------|
| GPT-4 零样本 | 67.0% |
| GPT-3.5 零样本 | 48.1% |
| GPT-3.5 + Agent 循环 | **95.1%** |

GPT-3.5（弱模型）+ 良好的 Agent 流水线（工具使用、反思、规划）大幅超越了 GPT-4（强模型）零样本。

这意味着你可以花精力优化模型内部的记忆系统，也可以花精力优化 Agent 外部的工具和流程。**后者的收益可能更高。**

### Anthropic 的 ACI 概念

Anthropic 在 2024 年 12 月的《Building Effective Agents》中提出了 **ACI（Agent-Computer Interface）** 的概念——Agent 与计算机之间的接口质量和 HCI 一样值得精心设计。

他们报告：

> "在 SWE-bench 的 Agent 上，**优化工具所花的时间比优化整体提示词还要多。**"

一个具体的案例：把工具参数从相对路径改成绝对路径（简单的防错设计），就消除了一整类错误。**不需要更好的记忆，不需要更强的模型，只需要想清楚工具该怎么暴露。**

这就是 Harness 工程的威力。

### MCP 和 A2A 的标准化信号

2024-2025 年，两个协议的出现标志着产业界意识到 Harness 层的重要性：

- **MCP（Model Context Protocol）**：标准化 Agent 如何访问工具和数据
- **A2A（Agent-to-Agent Protocol）**：标准化 Agent 之间如何通信

这两个协议不是在解决"模型怎么更聪明"，而是在解决"Agent 如何更好地与环境互动"。它们本质上都是 Harness 工程的标准化工件。

## 十、结论：什么是架构恒量

回到最初的问题：一个 1987 年的架构，凭什么在今天还有讨论价值？

### SOAR 做对了什么

SOAR 识别出了一些**通用智能系统的架构恒量**——不管用什么技术实现，这些结构都是必要的：

1. **不同的记忆服务于不同的目的**——程序性记忆（怎么做）、语义记忆（是什么）、情节记忆（经历过什么）。三种记忆不能互相替代。今天的产品试图用"文本注入"这一种机制覆盖所有记忆需求，这不可能够。

2. **决策需要竞争机制**——不是一条规则做所有决定，而是多条规则同时给出建议，通过竞争选出胜者。ReAct 的"Thought"本质上就是这个竞争过程，只不过用 LLM prompt 模拟而不是用偏好系统。

3. **经验需要编译成行为改变**——Chunking 是真正的学习：它改变了系统未来如何决策。今天所谓的"终身学习"只是存了更多文本让模型下次读，不是真正的行为层学习。

### SOAR 做错了什么

SOAR 的失败同样值得记住：

1. **纯符号无法解决接地问题**——符号 `^type block` 对系统本身没有意义。所有"理解"都是程序员手动赋予的。SOAR 接地到现实世界的唯一方式是有人写代码把传感器数据翻译成符号。

2. **知识获取瓶颈**——你写一条规则，它就有那一条知识。写 5200 条规则（TacAir-Soar 的规模）需要几个月甚至几年。LLM 从数据中学到了隐式的"规则"，绕过了这个瓶颈。

### 今天的 LLM Agent

LLM 解决了 SOAR 的两个致命问题（符号接地、知识获取），但在**架构层面**比 SOAR 更简陋：

| 架构需求 | SOAR 的方案 | 今天的方案 |
|:---------|:-----------|:-----------|
| 程序性记忆 | 规则 | 模型权重（隐式） |
| 语义记忆 | SMem + 检索 | RAG + 向量检索 |
| 情节记忆 | EpMem + 线索匹配 | 对话历史 + 摘要 |
| 决策机制 | 偏好系统 | ReAct prompt |
| 学习机制 | Chunking / RL | 微调 / prompt 缓存 |
| 目标管理 | Goal Stack | 隐式（在 prompt 里） |

### 真正该做的事

不是"SOAR 更好"或"LLM 更好"——而是弄清楚哪些是架构恒量（总得有不同种类的记忆，总得有决策循环，总得能从经验中学习），哪些可以交给神经网络。

SOAR 是一个探索性原型。它有些结构做对了，有些假设错了。今天 LLM Agent 换了一种方式做错不同的事。**真正有价值的方向不是选边站，而是把两个时代各自做对的部分拼起来。**

这让我想到一个更务实的路线。SOAR 和 LLM 不是二选一：

- **NL2GenSym（2025）** 已经在做这件事：LLM 从自然语言生成 SOAR 规则，SOAR 负责执行和学习
- **LLM-Modulo 认知系统**：LLM 处理模糊输入和开放域知识，SOAR 负责确定性的决策循环
- **游戏行业的现状就是混合架构**：行为树做核心决策（符号的确定性和可调试性），ML 做动画和感知（神经的灵活性）

符号系统没有消失，它退到了它该在的位置。神经网络也没有万能，它做不到的事情仍然需要一个结构化的外壳。

30 年过去了。也许该往前看了，但往前看的方向不是扔掉旧地图——而是搞清楚哪些线条仍然准确，哪些需要重新画。
